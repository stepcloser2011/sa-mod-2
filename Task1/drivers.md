Задание 1. Архитектурная диагностика и целевое видение

## 1. Анализ текущей архитектуры

### 1.1 Организационные ограничения

-   Ограниченный персонал. Выделенных SRE-инженера, технического
    писателя и бизнес-аналитика в компании нет;

-   Архитектура платформы не за документирована -- сложность поиска
    неисправностей;

-   Отсутствие возможности переписать систему полностью;

-   Требуется постепенная миграция на целевую архитектуру

### 1.2 Текушая нагрузка

-   До 15 000 RPS в пике на аукцион;

-   P95 времени отклика составляет 110--120 ms при требовании не более
    100 ms.

-   Периодические деградации в часы пик.

-   Отсутствие запаса по производительности.

### 1.3 Узкие места

-   Система AdScale работает на пределе своих возможностей по
    производительности

-   Ожидается существенный прирост нагрузки в процессе интеграции с
    DSP-платформой;

-   Единая БД для всех модулей как для высокочастотных запросов в
    реальном времени (RTB) так для аналитики со сложными SQL запросами;

-   Отсутствие резервирования БД и серверов приложений для продуктивной
    среды;

-   Синхронные коммуникации: проблемы производительности одного
    компонента влияет на связанные модули системы;

### 1.4 Архитектурные проблемы и ограничения

-   Монолитная (модульная) архитектура -- отсутствие возможности
    горизонтального масштабирования;

-   Возможности вертикального масштабирования ограничены монолитной
    архитектурой приложения;

-   Использование единой БД Postgres (сервер БД масштабируется только
    вертикально) также ограничивает производительность;

-   Отсутствие кеша для чтения из БД Postgres что снижает
    производительность по чтению из БД;

-   Скрытые зависимости --- общая БД создаёт сильную связанность между
    модулями;

-   Не используются очереди -- вся коммуникация между модулями
    синхронная.

-   Ручной деплой, отсутствие инструментов конвейера разработки и
    тестирования и соотв-но контейнеризация

### 1.5 Результаты анализа текущей архитектуры

-   Архитектура --- модульный монолит.

-   База данных --- одна PostgreSQL, все модули работают с общей схемой.

-   Отсутствие кеширования, поэтому каждый поиск билетов идёт напрямую в
    базу данных.

-   Доступно только ограниченное вертикальное масштабируеме.

-   Нет очередей, а все операции синхронные, так что при пиковой
    нагрузке потоки блокируются.

-   До 15 000 RPS в пике на аукцион;

-   Строгие требования по времени отклика: не более 100 ms для аукциона;

-   Высокая нагрузка на запись (события кликов и показов);

-   Постоянный поток событий (event stream).

### 1.6 Ключевые требования для выбора целевой архитектуры и миграции

-   Увеличение нагрузки на 20 процентов после миграции

-   Увеличение нагрузки в 2 раза через год

-   Время отклика сервиса аукционов до не более 80 ms для аукциона

-   Надежность изоляция сбоев, быстрое восстановление -- 99,9

-   Независимость работы компонентов/сервисов системы

-   Гибкого масштабирование системы

-   Невозможно переписать систему полностью, требуется постепенная
    миграция

> Архитектура в виде модульного монолита не решает основной проблемы ---
> конкуренцию за дисковую подсистему единственной инсталляции
> PostgreSQL. Очереди сообщений, кеширование, репикация/шардирование
> необходимы.

**Вывод** -- ключевые требования могут быть выполнены при переходе на
микросервисную архитектуру.

## 3. Выбор архитектурного стиля

### 3.1 Выбор метода миграции

### Сравнительный анализ альтернатив:

-   Модульный монолит: Позволяет упорядочить кодовую базу внутри единого
    процесса, однако не решает фундаментальных инфраструктурных проблем
    текущей системы --- отсутствия очередей, высокой конкуренции за I/O
    единственной инсталляции PostgreSQL и синхронных межмодульных
    вызовов. Данный подход недостаточен для обеспечения целевого P95 \<
    100 ms при росте нагрузки.

-   Переписать все с нуля («Big Bang»): Неприменима ввиду критического
    риска нарушения непрерывности бизнеса, отсутствия запаса
    производительности и высоких требований к компетенциям команды в
    области распределенных систем.

-   Паттерн «Strangler Fig» (Фиговое дерево-душитель): Является наиболее
    сбалансированным решением для долгосрочной перспективы, так как
    обеспечивает постепенный вывод легаси-компонентов из эксплуатации
    без остановки обработки трафика.

**Предлагается осуществить поэтапную стратегию, выбрав за основу
Strangler Fig** **Pattern** как наиболее универсальный подход в
постепенной и безопасной миграции на микросервисы.

[Strangler Fig Pattern - суть паттерна:]{.underline}

-   Пре реквизит: существующая монолитная система разделена на модули
    ([готово]{.underline});

-   Создается реверсивный прокси или шлюз для досутпа к модулям и
    перспективным микросервисам

-   Выбранный модуль (например, модуль аналитики) выносится в отдельный
    микросервис аналитики;

-   Реверсивный-прокси (или шлюз) направляет запросы следующим образом:

-   Существующий код в монолите обрабатывает все функции, кроме
    вынесенной,

    -   Новые запросы для модуля Статистики (например) перенаправляются
        в микросервис аналитики;

    -   Далее постепенно остальные модули выносятся в аналогичные
        микросервисы.

[Основные достоинства данного подхода:]{.underline}

-   Простой и понятный подход без дополнительной разработки.

-   Минимизируется риск: существующий код монолита остается в работе;

-   Возможность быстрого отката существующую архитектуру монолит

-   Позволяет разделить процесс перевода на отдельные шаги и решать
    задачу поэтапно;

Тем не менее, внедрение паттерна Strangler Fig без подготовки
инфраструктуры и решения первоочередных проблем с производительностью не
приведет к требуемым результатам , а только добавит сетевых задержек и
новых точек отказад

### 3.2 Стратегия миграции 

**1 этап. Повышение производительности,** создание инфраструктуры и
повышение производительности (18 000 RPS и соблюдение SLA (\< 80 ms
latency)) для дальнейшего внедрения целевого решения:

-   **Внедрение асинхронной модели записи** в существующей архитектуре.
    Сервер сбора статистики отключаются от прямого доступа к БД.
    Создается брокер сообщений (кластер Apache Kafka). Запись событий
    осуществляется через запись в топик со временем отклика \~1--2 мс.
    Далее запись в БД производится путем чтения из топика в фоновом
    режиме.

-   **Разделение транзакционных и аналитических потоков.**
    Разворачивается Read Replica PostgreSQL. SELECT-запросы сервиса
    аналитики и рекламного кабинета полностью перенаправляются на
    реплику.

-   **Создание единой точки входа**. Создается реверсивный прокси перед
    внешними системами и пользователями, которая в последующем будет
    выполнять роль API Gateway (Envoy,Traefik, NGINX+, HAProxy) для
    управления маршрутизацией, аутентификацией и применения политик
    Circuit Breaker.

**2 этап** Постепенный вынос модулей/сервисов в микроервисы согласно
выбранному паттерну Strangler Fig

-   **Изоляция сервисов статистики и аналитики.** Создается независимые
    микросервисы статистики и аналитики с собственными БД (или репликой
    БД). Монолит выступает исключительно в роли источника данных
    (событий) в Kafka.

-   **Повышение времени отклика для чтения из БД**. Внедряется
    кеширование данных в Redis Cluster для исключения блокировок
    PostgreSQL БД.

-   **Вынос бизнес-логики в отдельный высокопроизводительные
    микросервисы** (C++/Go), доступ к которому осуществляется по gRPC.
    Это повышает производительность и снижает сложность системы в целом.

-   **Управление данными**. Создание выделенных БД для новых
    микросервисов. Запрет на прямые SQL-обращения новых сервисов к
    таблицам старого монолита. Синхронизация данных новых БД с мастер
    данными в существующей БД через механизм Change Data Capture
    (Debezium).

-   **Изоляция финансовых других операций.** Финансовые расчёты также
    становятся асинхронным и исключатся из критического пути ответа на
    ставку. Также выносятся в микросервисы оставшиеся модули/сервисы.

**3. Этап** Горизонтальное масштабирование и финальная миграция

-   **Шардирование** наиболее нагруженных таблиц для БД аукциона по мере
    роста нагрузки.

-   **Повышение количества реплик** наиболее нагруженных сервисов по
    мере роста нагрузки и балансировка на них через API Gateway

-   **Мультирегиональное развертывание**. Архитектура разворачивается в
    нескольких зонах доступности. Глобальный балансировщик DNS
    направляет трафик в ближайший регион, снижая сетевую задержку (RTT).
